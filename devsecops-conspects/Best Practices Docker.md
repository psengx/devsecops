>При использовании команды`FROM`в Dockerfile мы часто получаем в нагрузку много системного мусора. Это раздувает не только размер образа, забивая диск, но это также огромная дыра в безопасности. И здесь важно следующее:

## 1. Выбор минимально возможного образа

Здесь есть три пути:

1. Использование Alpine Linux размером в 5MB.
   Этот подход применим идеально для Go или статических бинарников.
2. Использование Slim-версии. 
3. Distorless. Тут нет вообще ничего, кроме самого runtime языка и приложения. Там нет пакетного менеджера, нет Shell. Но мы тоже не можем туда зайти (с помощью `docker exec`)

## 2. Тег `latest`

Его использование в продакшене = риск. При выходе новой версии с ломающими изменениями в приложении, наш CI автоматически её подтянет, пересоберёт образ и выкатит в прод. Сервис упадёт. 

**Поэтому нужно прописывать конкретную версию.**

## 3. Использование файла `.dockerignore`

Механика `docker build`:
- взять всё содержимое текущей директории
- архивировать его
- отправить докер демону
Но в корне проекта могут лежать различные папки по типу .git, локальные логи, какие-то модули, всё это также отправится демону, что забивает сеть и создаёт риски безопасности.

Поэтому используют файл `.dockerignore`. Туда пишут все те вещи, которые нужно проигнорировать при сборке. 

## 4. Кэширование зависимостей

Каждая инструкция в Dockerfile создаёт новый слой, и Docker кэширует каждый из них. Но при изменении одного слоя, все последующие автоматически пересобираются с нуля. 

Например, есть Dockerfile:

```Dockerfile
COPY . .
RUN npm install
```

При малейшем изменении файла директории, Docker видит, что файлы для копии изменились. Хэш слоя меняется, а кэш сбрасывается. И следующая команда RUN запускается заново и всё заново выкачивается.

>Нужно отделять зависимости от кода!

Сначала копировать только файлы манифестов, а затем, уже при установленных и **закэшированных** зависимостях мы копируем код. И пока мы не трогаем файлы, отвечающие за установку зависимостей, слой с установкой зависимостей будет браться из кэша.

## 5. Использование составной команды RUN

Каждая команда RUN создаёт новый слой, доступный только для чтения. 

Имеем такой Dockerfile:

```Dockerfile
RUN apt-get update
RUN apt-get install -y vim
RUN rm -rf /var/lib/apt/lists/*
```

Физически создаётся 3 слоя: сначала скачиваем пакеты для обновления, затем поверх них скачали Vim, а потом третьим слоем пометили файлы из слоя A как удалённые. В итоговом контейнере мы не увидим эти файлы, но внутри образа они остались. Эти файлы будут каждый пуш и пул ходить по сети...

Нужно объединить связанные команды в один атомарный слой. Для этого используются оператор `&&` и `\` для переноса строк:

```Dockerfile
RUN apt-get update && \
apt-get install -y vim && \
rm -rf /var/lib/apt/lists/*
```

Теперь при запуске контейнера все команды выполняются в рамках одного слоя. После чего фиксируется только полезный результат (здесь - Vim).

## 6. Всегда использовать `COPY` для переноса локальных файлов

Так как ADD является антипаттерном из-за своей непредсказуемости (неизвестно, произойдет копирование или распаковка) и проблем с кэшем (при скачивании файла по url, докер каждый раз будет делать запрос к серверу, чтобы проверить метаданные файла. При ином ответе сервера, кэш слоя слетит и сборка замедлится). 

`ADD` следует использовать только в одном случае - когда нам гарантированно нужно распаковать локальный архив в одну строчку. Для скачивания сети использует просто `RUN` (а внутри url или viget).

## 7. Multi-stage Build

Суть: описание всего процесса в одном Dockerfile, НО деление его на логические этапы.

Пример реализации multistage сборки:

```Dockerfile
# --- Сборка (Builder)
FROM golang:1.21-alpine AS builder
WORKDIR /app
# Кэширование зависимостей (как [[Best Practices Docker#4. Кэширование зависимостей|тут]])
COPY go.mod do.sum ./
RUN go mod download

COPY . .
# Сборка статического бинарника с именем myapp
RUN go build -o myapp main.go

# --- Запуск (Production)
# Новый FROM обнуляет всё, что было до этого
FROM alpine:latest
WORKDIR /app
# Копирование не с локальной машины, а из этапа "builder"
# ТОЛЬКО одного файла, а не всех
COPY --from=builder /app/myapp
# Запуск приложения
CMD ["./myapp"]
```


## Использовать BuildKit
Старый сборщик читал Dockerfile сверху-вниз линейно, а BuildKit строит граф зависимостей. Он смотрит на файл и понимает, что если сборки между собой никак не связаны (например, фронт и бек), то их можно запустить одновременно на разных ядрах.
## 8. Всегда создаем непривилегированного пользователя и переключаемся на него

По умолчанию докер запускает всё из-под root. Это удобно для разработки, никаких ошибок с доступом. Но по безопасности это плохо. В линуксе root внутри контейнера - это тот же самый root на хостовой машине. 

```Dockerfile
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
WORKDIR /app
# При копировании файлов сразу отдаем их юзеру
COPY --chown=appuser:appgroup
USER appuser
CMD ["...", "..."]
```

## 9. Использовать механизм Build Secrets (требует BuildKit)

Как это выглядит в Dockerfile:

```Dockerfile
RUN --mount=type=secret, id=mytoken \
export TOKEN=S(cat /run/secrets/mytoken) && \
npm install
```

А это команда для запуска такого образа:

```shell
docker build --secret
id=mytoken,src=./local_secrets.txt .
```

Как это работает физически:
1. BuildKit берет файл с секретом с хоста
2. Монтирует его в специальную папку внутри контейнера (временная папка во время выполнения конкретной команды RUN)
3. И как только RUN завершилась, этот слой фиксируется, но файла с секретом в нём уже нет

## 10. PID процессов и получение запросов
В линуксе процесс с PID 1 особенный и ядро относится к нему иначе, чем к остальным. Если в Dockerfile написать запуск через shell-скрипт, то процессом с PID 1 становится bash или shell, а приложение запускается как дочерний процесс, из-за чего при попытке остановить процесс приложения, сигнал приходит bash/shell и он не передаст сигнал дочерним процессам. 

Избежать этого можно через `exec`:

```Bash
#! /bin/sh
echo "Starting app..."

exec node index.js
```

При использовании entrypoint-скриптов, то запуск финальной команды всегда происходит через exec, потому что она не создает новый процесс, а замещает текущий процесс нашим приложением. Тогда PID будет = 1.

Второй способ - использовать `tini`:

```Dockerfile
# Установка tini
RUN apk add --no-cache tini
# Используем его как точку входа
ENTRYPOINT ["/sbin/tini", "--"]
# Запуск приложения как аргумента
CMD ["node", "app.js"]
```

PID=1 теперь у процесса `tini`. Он ловит сигналы от Kuber'а и проксирует их приложению. А также он собирает zombie-процессы, что полезно для долгоживущих контейнеров. 

## 11. Слепота докера: состояние контейнера через HEALTHCHECK

Docker по умолчанию судит о здоровье контейнера только по признаку - работает ли процесс. Если процесс есть, то у него статус Up. Но с приложение может попасть в deadlock, потерять коннект, уйти в бесконечный цикл - и процесс будет висеть и кушать память, но на запросы отвечать не будет. Это так называемый zombie-контейнер. А Kuber будет продолжать слать туда трафик.

Пример реализации инструкции HEALTHCHECK:

```Dockerfile
# Проверка каждые 30 секунд. Если ответа нет 3 секунды -> fail
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s \
CMD curl -f http://localhost:8080/health || exit 1
```

Эта инструкция заставляет докер демона периодически запускать команду внутри контейнера. И если она вернет ошибку, статус контейнера сменится с Up на Unhealthy. Тогда оркестратор (Kuber) это увидит и перестанет слать туда трафик. А если настроено, то даже перезапустит зависший контейнер.
